# Opt-in DCC-EX network control

A new database defaults to SIMULATION with no station connection or track-power command. Connection settings and the last selected mode are persisted in the database. **A restart is not a safety reset:** when a Home Assistant mains plug is configured and reports on, the background monitor can automatically connect to the configured station and select HARDWARE mode; an existing database can also restore HARDWARE mode. The monitor does not itself turn on rail power or run a sequence. Configure only a *verified* CSB1 IP/hostname and TCP port, and independently verify station state and physical power before operating. Do not guess decoder addresses: roster IDs are database IDs, whereas the hardware throttle only accepts numeric `address` values already in the configured roster. An unverified/missing roster address cannot operate hardware. Points with configured DCC accessory addresses (1–2044) can send native `<a address 0|1>` commands in HARDWARE mode when connected, powered, and not emergency-stopped. This records the sent command, not feedback on the actual point position. Turntable control has no physical protocol mapping and is rejected in HARDWARE mode.

## Local-only operation

Bind the production backend to `127.0.0.1` and do not publish it, port-forward it, or serve it through an internet-facing reverse proxy. Peer-address and browser-origin checks are not internet-grade authentication: a proxy can make external requests appear to come from loopback, including inventory and plug setup routes. The optional `WORKSHOP_LAN_SUBNET` mode allows token-free hardware operation by permitted peers; avoid this mode for a public release installation. Without it, set a fresh `WORKSHOP_OPERATOR_TOKEN` or hardware routes return 503. The frontend does not send the token, so the supplied local UI remains simulation-first. Vite dev/preview may bind all interfaces and proxy API requests to loopback; do not expose those servers on untrusted networks. See the root README for setup and data backups.

`GET /api/hardware` and `/api/state` return connection/mode/power status. Power is considered enabled only after a matching native `<p1>` acknowledgement. A timeout or transport error attempts `<0>`, drops the connection, and reports 503. Command requests in HARDWARE mode require connection and verified power. `POST /api/emergency-stop` sends native `<!>` followed by `<0>` whenever connected, **even while mode is SIMULATION**; it latches the local stop before the send. Disconnect attempts `<0>` but its physical success cannot be guaranteed. Software E-stop and track-power status are not an independent, safety-rated power cut: provide a physical power switch/kill mechanism, keep the layout supervised, and verify the station state independently after network failure.

## Protocol evidence and limitations

DCC-EX [Consolidated command reference](https://dcc-ex.com/reference/software/command-summary-consolidated.html) documents ASCII native `<...>` commands: `<1>`/`<0>` main track power with `<p1>`/`<p0>` reports, `<t cab speed direction>` throttle, `<F cab function onoff>` function, `<a address 0|1>` accessory point command, and `<!>` emergency stop. This adapter sends framed commands over a configured TCP socket; no WiThrottle protocol is implemented. The [EX-CSB1 WiFi configuration](https://dcc-ex.com/ex-commandstation/rtr-wifi-setup.html) confirms onboard WiFi and direct throttle connections, but warns that WiFi/Ethernet PC-style connections can be functionally limited and are not supported for the JMRI use case. Confirm that *your installed firmware and selected port* accept native DCC-EX commands before attempting physical control. No device discovery or physical commands occur during backend tests (fake sockets only).
